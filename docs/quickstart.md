# Quickstart

From nothing to text generated by an 8-billion-parameter LittleBit model on a 6 GB laptop GPU. LittleBit stores each
weight matrix as two low-rank sign matrices plus a few scale vectors, well below 1 bit per weight; LittleMore runs such
models through a patched llama.cpp engine (terms are explained in the glossary of [development.md](development.md)).

Tested on Windows 11 with an RTX 4050 Laptop GPU (6 GB), an Intel Core i7-13620H and 16 GB of RAM.

## 1. Install

LittleMore is not on PyPI yet: build it from a source checkout and install the wheel.

1. Set up the tools and the Python environment ([setup-windows.md](setup-windows.md)) and build the engine and the C
   library ([development.md](development.md), sections 2 and 2b).
2. Build and install the wheel:

   ```powershell
   .venv\Scripts\python.exe -m build --wheel --outdir dist python
   .venv\Scripts\python.exe -m pip install (Get-ChildItem dist\littlemore-*.whl)
   ```

What the wheel needs on the machine:

- **Microsoft Visual C++ Redistributable** (2015-2022, x64): the bundled DLLs import `VCRUNTIME140`, `MSVCP140` and
  `VCOMP140`. It is usually installed already; if Python reports that `littlemore.dll` or a plugin cannot be loaded,
  install it from Microsoft.
- **For the GPU: an NVIDIA driver and the CUDA 12 runtime DLLs** (`cudart64_12.dll`, `cublas64_12.dll`,
  `cublasLt64_12.dll`). The wheel does not include them (cuBLASLt alone is 640 MiB). Install the CUDA 12 toolkit, or
  `pip install "littlemore[cuda]"` (NVIDIA's runtime wheels; this route is not tested yet). Without them LittleMore
  still runs on the CPU (and on Vulkan).
- **No `PATH` changes**: Python does not search `PATH` for the libraries a DLL depends on, so the SDK registers the CUDA
  folders itself with `os.add_dll_directory()` (from `CUDA_PATH`, `PATH` folders that contain `cudart64_*.dll`, the
  NVIDIA runtime wheels and the default toolkit folders). If the GPU is not found, point `LITTLEMORE_DLL_DIR` at the
  folder with the CUDA runtime DLLs.

Check what LittleMore sees (`CUDA0` must be listed for the GPU to be used):

```powershell
python -c "import littlemore; print([b['name'] for b in littlemore.backends_info()])"
# ['CUDA0', 'Vulkan0', 'Vulkan1', 'CPU']
```

## 2. Get a model

The example uses the community checkpoint
[`LittleBitLLM/littlebit-qwen3-8b-0.55bpw`](https://huggingface.co/LittleBitLLM/littlebit-qwen3-8b-0.55bpw):
Qwen3-8B compressed to 0.55 bits per weight with LittleBit-2 and recovered with half an epoch of quantization-aware
distillation (2.97 GB download). See "Licences" below before you use it.

```powershell
.venv\Scripts\hf.exe download LittleBitLLM/littlebit-qwen3-8b-0.55bpw `
    --revision 6b2c47aa9707e624e2e737d16d64a66be8090ae9 `
    --local-dir .cache/models/littlebit-qwen3-8b-0.55bpw --exclude "logs/*" "runs/*"
```

## 3. Convert it to GGUF

The engine reads one GGUF file. The converter needs the development environment (PyTorch, transformers and the
engine's GGUF writer), so run it from the source checkout:

```powershell
littlemore convert .cache/models/littlebit-qwen3-8b-0.55bpw -o .cache/gguf/littlebit-qwen3-8b-0.55bpw-b1.gguf
```

(`littlemore convert` runs `tools/convert/lb_to_gguf.py`; `python -m tools.convert.lb_to_gguf` is the same.) It
writes a 2.84 GiB file (2905 MiB): 490 MiB of 1-bit sign matrices, the token embedding and the output head in F16
(1.16 GiB each, the largest part of the file) and the norms and scales in F32. After writing, it reads every one of the 252 LittleBit
layers back from the file and compares it with an independent float64 evaluation of the checkpoint; any difference
aborts the conversion and leaves no file behind.

Measured for this model: 2.5 to 3 minutes (about 2 minutes of it is the read-back check), at most 4.9 GiB of RAM (the
layers are processed one at a time). The converter estimates its memory need first and stops with a message if the
free RAM is clearly too small. `--head-type q8_0` (or `q6_k`) stores the embedding and the head in 8 (or 6.6) bits per
value instead of 16: a smaller file and faster generation, at a small accuracy cost (measured on Qwen3-0.6B and 1.7B in
[bench/results/phase1.md](../bench/results/phase1.md), not on this model); the 8B model fits a 6 GB GPU without it.

## 4. Run it

```powershell
littlemore run .cache/gguf/littlebit-qwen3-8b-0.55bpw-b1.gguf --prompt "Hello"     # one answer, then exit
littlemore run .cache/gguf/littlebit-qwen3-8b-0.55bpw-b1.gguf                      # chat in the terminal
littlemore bench .cache/gguf/littlebit-qwen3-8b-0.55bpw-b1.gguf                    # load time and speed
```

From Python:

```python
import littlemore

with littlemore.Model(".cache/gguf/littlebit-qwen3-8b-0.55bpw-b1.gguf") as model:   # n_gpu_layers="auto"
    print(model.generate("The capital of France is", max_tokens=32, temperature=0))
    info = model.info()["model"]
    print(info["n_gpu_layers"], "of", info["n_layer"] + 1, "layers on", info["gpu_devices"])
```

Output (greedy, so the same every time):

```
 Paris, and the city is the capital of the French Republic. The capital is located in the French Riviera, which is the French Riviera, the French
37 of 37 layers on CUDA0
```

`model.chat(messages)` applies the model's chat template; `stream=True` returns the text piece by piece. The full API
is in [python/README.md](../python/README.md).

## 5. GPU or CPU

- **Auto-fit** (the default, `n_gpu_layers="auto"`, CLI `-ngl auto`): before loading, LittleMore estimates the size of
  every layer and its cache and puts as many layers on the GPU as the free GPU memory allows. For this model on a
  6 GB GPU that is everything: 36 layers plus the output head, 2703 MiB of GPU memory in use with the default
  4096-token context. A number (`n_gpu_layers=20`) sets the count yourself.
- **`n_gpu_layers=0` still uses the GPU** for long prompts (it processes prompt batches of 32 tokens or more there,
  which makes prompts much faster; here 1613 MiB of GPU memory), while generation runs on the CPU. This is intended.
- **`devices="none"`** (CLI `--cpu-only`) uses no GPU at all: only the CPU computes and no GPU memory is allocated for
  the model (loading the backends alone shows about 70 MiB in `nvidia-smi`).
- On Windows the driver does not report other programs' GPU memory reliably. If another program uses a lot of it, set
  `vram_budget` (bytes) so the fit does not overcommit.

## 6. Speed

Measured with `llama-bench` through `bench/run_bench.py` (median of 10 repetitions, 3 interleaved rounds for the GPU
row; 3 repetitions, 1 round for the others; GPU SM clock 1.5 to 2.3 GHz during the runs). Raw results:
`bench/results/community_8b_*.json`.

| Setting | Generation, tokens/s | Prompt (512 tokens), tokens/s | GPU memory |
|---|---|---|---|
| all layers on the GPU (what auto-fit picks) | 63.5 | 1223 | 2197 MiB (llama-bench) / 2703 MiB (SDK, 4096 context) |
| `n_gpu_layers=0` (GPU only for prompt batches) | 13.3 | 735 | 1667 MiB (llama-bench) |
| CPU only (`devices="none"`, 10-core i7-13620H) | 13.4 | 41 | none |

Through the SDK, 32 greedy tokens took 0.59 s on the GPU (first piece after 82 ms, then 61.5 tokens/s) and 3.0 s on the
CPU only.

## 7. Quality: what to expect

**This checkpoint is far below the original model**, and it is an early one:

- Its model card reports WikiText-2 perplexity 24.48 against 9.73 for the original Qwen3-8B (lower is better), C4
  32.10 against 13.30, and ARC-Challenge 19.5 % (chance level) against 55.5 %. It was trained for 0.5 epoch, a tenth
  of what the LittleBit paper uses; the card expects large gains from longer training.
- LittleMore reproduces the card's number: WikiText-2 perplexity **24.49** (engine on the GPU, 2048-token windows,
  every token scored, the test split joined as the card's evaluation does: 299078 tokens, 146 windows; see the note
  below), against 24.48 on the card.
- In practice the continuations are fluent for a few words and then repeat or drift (see the example above), and
  a chat answer through the chat template was not usable in our test (one question; the answer degenerated into
  repeated question marks; the distillation data was plain text). Use it
  to try sub-1-bit inference, not for real tasks.
- Init-only checkpoints (made without any training, e.g. by `tools/dev/make_lb2_init.py` for testing) produce
  meaningless text: they exist to test the software, not the method.

Correctness, separately from quality: on the first 32 chunks of 512 tokens of WikiText-2 (the setting of the
project's perplexity parity test), the engine and an independent float32 PyTorch evaluation of the checkpoint
(`tools/dev/reference.py`) agree within 0.1 % on the GPU (21.653 against 21.632) and within 0.0002 % on the CPU with
exact attention settings (21.63250 against 21.63247). The small GPU difference comes from the output head: for prompt
batches, cuBLAS multiplies the F16 head with 16-bit accumulation; with `GGML_CUDA_CUBLAS_COMPUTE_TYPE=f32` (an
llama.cpp setting) the GPU result is 21.6322, and generation speed and prompt speed did not change measurably.

Note on the perplexity settings: the card's value comes from the LittleBit evaluation script; its log in the model
repository shows 299078 tokens in 146 windows, i.e. non-overlapping 2048-token windows over the test split joined with
blank lines (that join gives exactly 299078 tokens with this tokenizer), and the usual evaluation of that kind scores
every token. `llama-perplexity` by default scores only the second half of each window; its strided mode with
`-c 1025 --ppl-stride 2047 -b 1024` gives 2048-token windows that score every token once (the windows start every
2047 tokens instead of every 2048), which is the comparable setting used above. With the default mode at 512 tokens (only the second half of each window scored) the first
32 windows give 21.65.
